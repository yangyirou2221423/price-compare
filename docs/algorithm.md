# 算法与复杂度

## 1. 问题定义

给定：

- 一个标准商品（或购物车中的多件商品）；
- 每个平台的一条报价（价格、运费、店铺）；
- 报价上的一组优惠/补贴；
- 用户上下文：地区、会员、以旧换新估值、排序偏好、日期。

求：每个平台的最低实付（以及净价），以及达到该价格的优惠使用序列。

目标函数：

```
final(price) = max(0, 商品价 - 支付类优惠) + 运费
net(price)   = max(0, 商品价 - 支付类优惠 - 返利 - 赠品估值) + 运费
```

默认按 `(final, net)` 字典序排序；用户选择“净价优先”时按 `(net, final)`。

## 2. 优惠模型

每条 `Benefit`：

| 字段 | 含义 |
|---|---|
| `kind` | 店铺券、平台券、品类券、满减、会员、平台补贴、国补、以旧换新、支付立减、返利、赠品 |
| `value_type` | fixed / percent / per_threshold / price_override |
| `value` / `max_discount` | 金额或百分比，以及封顶 |
| `threshold` / `threshold_base` | 门槛，按原价或当前价判断 |
| `stage` | 使用阶段，保证顺序 |
| `stack_group` | 同组最多用一张 |
| `exclusive_with` | 显式互斥 |
| `requires` | 地区、会员、以旧换新、首单、最小数量 |
| `price_cap` / `price_cap_base` | 补贴价格上限 |
| `valid_from` / `valid_to` | 生效期 |

### 金额计算

```
fixed:          min(value, current_price)
percent:        min(current_price * value / 100, max_discount)
per_threshold:  floor(base / step) * value，封顶
price_override: 用活动价替换基础价（只在预处理阶段使用）
trade_in:       min(旧机估值 + value, current_price)
rebate/gift:    不降低支付金额，只降低净价
```

## 3. 单商品求解

### 3.1 预处理

1. 把国补/地区加码/以旧换新规则物化为 `Benefit`。
2. 合并报价自带优惠与规则优惠，按 `id` 去重。
3. 选出最低的合法活动价（`price_override`）作为基础价，并写入执行轨迹。
4. 其余优惠进入可选集合，按 `(stage, id)` 排序。

### 3.2 搜索

状态：

```
price        当前商品价（未加运费）
net_delta    返利 + 赠品估值（只影响净价）
used         已使用优惠 id 集合
used_groups  已占用 stack_group
stage        当前阶段
trace        执行轨迹
```

每一层：

- 先把当前状态作为一个候选解（允许不再使用任何优惠）。
- 从“未使用且 stage ≥ 当前阶段”的优惠中，逐个检查资格。
- 对合法优惠计算金额，得到新状态并递归。
- 同一阶段的不同顺序也会被枚举，因为百分比/固定金额/门槛可能对顺序敏感。

### 3.3 分支限界

对剩余优惠做乐观上界：

```
payment_bound = Σ 剩余支付类优惠的 max(0, 理论最大金额)
net_bound     = Σ 剩余净价类优惠的 max(0, 理论最大金额)

optimistic_final = max(0, price - payment_bound) + shipping
optimistic_net   = max(0, price - payment_bound - net_bound) + shipping
```

若 `optimistic_key >= best_key`（字典序），则剪枝。上界刻意忽略互斥和未来门槛，保证不会误剪。

### 3.4 记忆化

键：

```
(used_mask, stage, round(price * 100))
```

值：该状态下已见过的最高 `net_delta`。同一状态若净价收益不更优，直接返回。由于未来可选优惠只依赖 mask/stage/price，记忆化不影响最优性。

### 3.5 规模与退化

- 单商品优惠数通常 ≤ 15；超过 `MAX_EXACT_BENEFITS = 18` 时退化为贪心，并标注 `optimal=false`。
- 最坏复杂度 `O(2^n · n)`；剪枝与记忆化让实际运行在毫秒级（见第 7 节）。

### 3.6 解释生成

求解完成后：

- 已使用优惠：记录阶段、金额、执行前后价格。
- 未使用优惠：用最优状态检查资格，给出“差多少门槛 / 与谁互斥 / 地区不符 / 超出价格上限 / 非最优组合”等原因。
- 备选平台：给出与最优的差额，以及导致差额的主要资格原因。

## 4. 购物车拆单

### 4.1 行级定价

先只应用 `scope ∈ {item, shop}` 的优惠：

- 店铺券；
- 商品级国补；
- 活动价；
- 行级运费。

得到每件商品在各平台的“行价”。这一步复用单商品求解器，但限定作用域。

### 4.2 平台分配

把“每件商品去哪买”建模为划分：

```
m 件商品，p 个平台 → 最多 p^m 种分配
```

- 去重合并相同商品。
- `m ≤ 7` 且 `p^m ≤ 100,000` 时精确枚举。
- 超过规模：贪心分配 + 最多 3 轮局部搜索，标注非全局最优。
- 每个分配下，按平台分组求解订单。

### 4.3 订单级求解

同一平台的商品合并为一单，应用 `scope ∈ {platform, order}` 的优惠：

- 平台券、品类券；
- 跨店满减；
- 会员折扣；
- 平台补贴；
- 以旧换新（整单一次）；
- 支付立减；
- 返利/赠品（只影响净价）。

订单级求解复用与单商品相同的 DFS + 分支限界逻辑，状态是订单小计而不是单品价格。合成一个 `list_price = 订单标价小计` 的虚拟 Offer，使门槛/每满减判断复用同一套规则。

### 4.4 基线与节省

- 基线：所有商品放在同一个平台（对每个平台求一次，取最优）。
- 节省：`baseline_payment - optimized_payment`。
- 若拆单没有更省，明确输出“当前组合下拆单没有比单平台更省”。

### 4.5 凑单建议

对订单级“门槛未满足”的拒绝项：

```
gap = threshold - 当前小计
```

遍历候选商品（排除已在购物车中的），把候选加入该订单后重新求解：

```
净增 = 新订单实付 - 原订单实付
```

过滤掉仍未触发门槛的候选，按净增升序取前 3。若净增为负，说明“加购后实付反而下降”。

示例：

```
扫地机 2920 元，京东满 3000 减 300，差 80 元
加购 89 元收纳盒 → 小计 3009 → 减 300 → 实付 2709
净增 = 2709 - 2920 = -211 元
```

## 5. 政策规则引擎

规则 JSON 示例：

```json
{
  "id": "R-APPLIANCE-15",
  "name": "家电购新补贴（示例）",
  "type": "national_subsidy",
  "regions": ["全国"],
  "categories": ["家电"],
  "platforms": ["jd", "taobao", "pdd", "douyin"],
  "price_cap": 6000,
  "price_cap_base": "list",
  "percent": 15,
  "max_discount": 500,
  "stage": 6,
  "effective_from": "2026-01-01",
  "effective_to": "2026-12-31",
  "version": "2026.1"
}
```

判定流程：

1. 品类、平台、地区、生效期；
2. 会员/以旧换新资格；
3. 价格上限；
4. 物化为 `Benefit`，进入统一求解；
5. 不符合时返回可读原因。

地区加码与国补使用不同的 `stack_group`，因此可以叠加；同类补贴使用同一组，保证最多一张。

## 6. 价格历史与“先涨后降”

统计量：

- 90 天中位价、P25/P75、最低/最高；
- 当前分位 = 历史价格中 ≤ 当前价的比例；
- 7 天变化；
- 30 天/90 天最低。

疑似先涨后降：

```
pre_max = 近 16 天到近 3 天窗口内的最高价
fake_drop = pre_max ≥ 中位价 × 1.06
        且 当前价 ≤ 中位价 × 0.95
        且 当前价 ≤ pre_max × 0.90
```

该规则用于演示，不构成对任何平台的指控；页面文案使用“疑似”。

## 8. 正确性

- 黄金场景：P001/P002/P004/P005/P011 等固定预期值。
- 差分测试：随机生成 100 组小规模优惠（3–6 条），对比“无剪枝暴力枚举”和“分支限界”的 `final` 与 `net`，全部一致。
- 不变量：
  - 最终价 ≥ 0；
  - 使用的优惠都满足资格、门槛、互斥、有效期；
  - 互斥优惠不会同时出现；
  - 结果可复现（固定输入与规则）。
- API 测试覆盖 404、参数校验、购物车、历史、补贴、提交、适配器状态。

## 9. 已知简化与未来工作

| 简化 | 影响 | 未来 |
|---|---|---|
| 同一平台商品合并为一单 | 未覆盖多店铺多地址 | 按店铺/地址拆分订单 |
| 优惠按订单/商品作用域简化 | 未覆盖“第 N 件半价”等 | 支持数量阶梯与商品组合 |
| 返利按实付比例估算 | 未考虑提现门槛/到账时间 | 引入返利规则与时间价值 |
| 价格为静态快照 | 不反映实时波动 | 接入联盟 API/合规数据源 |
| 超过 18 条优惠用贪心 | 可能非最优 | ILP/OR-Tools 或分支定价 |
| 购物车 > 6 件用启发式 | 可能非全局最优 | 更大规模 ILP / 动态规划 |

## 10. 为什么不用现成 ILP

- 题目规模小（单商品 ≤ 18 条优惠、购物车 ≤ 6 件），精确搜索 + 剪枝足够快；
- 自研求解器可以记录完整决策轨迹，解释“为什么没选这张券”；
- 零重型依赖，部署简单，答辩时能讲清楚每一步；
- 未来需要更大规模时，可将单商品/订单级子问题替换为 ILP，外层仍保留平台分配枚举。
